## 🤖 DeepSeek

Вот структурированный список команд для диагностики и мониторинга Linux, сгруппированных по задачам:

### 🐧 Общая информация о системе
*   `uname -a` - показать всю информацию о системе и ядре
*   `hostname` - отобразить имя компьютера
*   `uptime` - показать время работы системы и среднюю нагрузку
*   `date` - вывести системную дату и время
*   `w` - показать, кто залогинен в систему

### ⚙️ Информация о процессоре (CPU)
*   `lscpu` - вывести подробную информацию о процессоре
*   `cat /proc/cpuinfo` - отобразить детальную информацию о CPU
*   `mpstat` - показать статистику использования CPU (из пакета `sysstat`)
*   `top` / `htop` - интерактивный мониторинг процессов и загрузки CPU в реальном времени

### 🧠 Информация о памяти (RAM и Swap)
*   `free -h` - показать использование оперативной памяти в удобном формате
*   `cat /proc/meminfo` - вывести детальную информацию о памяти
*   `vmstat` - показать статистику виртуальной памяти и системы
*   `swapon --show` - отобразить используемые файлы подкачки (swap)

### 💾 Информация о дисках и файловых системах
*   `df -h` - показать использование дискового пространства
*   `du -sh *` - анализ использования места каталогами
*   `lsblk` - вывести информацию о блочных устройствах (дисках)
*   `cat /proc/mounts` - отобразить смонтированные файловые системы
*   `smartctl -a /dev/sda` - проверить состояние жесткого диска через SMART
*   `hdparm -tT /dev/sda` - протестировать производительность чтения с диска

### 🌐 Сетевая диагностика
*   `ip addr` (или `ifconfig`) - показать настройки сетевых интерфейсов
*   `ss -tulpn` (или `netstat -tulpn`) - отобразить открытые порты и сетевые соединения
*   `ping` - проверить сетевое соединение с хостом
*   `traceroute` / `mtr` - диагностировать маршрут до узла
*   `nslookup` / `dig` - диагностика разрешения доменных имен
*   `ethtool` - получить информацию о сетевых устройствах

### 📜 Просмотр логов и сообщений ядра
*   `dmesg` - показать сообщения ядра (включая аппаратные ошибки)
*   `journalctl` - просмотреть системные логи (для systemd)
*   `tail -f /var/log/syslog` - в реальном времени следить за системным журналом
*   `last reboot` - показать историю перезагрузок системы

### 📊 Мониторинг производительности и ввода-вывода (I/O)
*   `iostat` - статистика ввода-вывода для дисков
*   `iotop` - мониторинг дисковой активности в реальном времени
*   `pidstat` - статистика по процессам (из пакета `sysstat`)
*   `sar` - сбор, отчет и сохранение информации о производительности

### 🖥️ Информация об оборудовании
*   `lspci` - список всех PCI-устройств
*   `lsusb` - список всех USB-устройств
*   `lshw` - подробная информация обо всем оборудовании
*   `dmidecode` - информация об аппаратных компонентах (SMBIOS/DMI)
*   `inxi` - скрипт для отображения конфигурации системы и оборудования
*   `hwinfo` - детальный анализ оборудования

### 🛠️ Продвинутая диагностика
*   `strace` - отслеживание системных вызовов процессов
*   `perf` - профилирование производительности CPU
*   `tcpdump` - анализ сетевого трафика
*   `lsmod` - список загруженных модулей ядра

> **Важно:** Некоторые команды (например, `smartctl`, `dmidecode`, `hdparm`) могут требовать прав суперпользователя (`sudo`). Часть утилит (из пакетов `sysstat`, `smartmontools` и др.) возможно, потребуется установить отдельно.

### 🌐 Сетевой мониторинг и обнаружение уязвимостей

*   `nmap` — сканирование сети, обнаружение хостов, открытых портов и сервисов.
    *   `nmap -sn <сеть>` — быстрое обнаружение активных хостов.
    *   `nmap -sS -sV -O <цель>` — детальное сканирование портов, версий служб и ОС.
    *   `nmap --script vuln <цель>` — проверка на известные уязвимости с помощью скриптов.
*   `netstat -tulnp` / `ss -tulnp` — просмотр открытых портов и прослушиваемых служб.
*   `tcpdump` — захват и анализ сетевого трафика в реальном времени.
*   `iftop` — мониторинг сетевой активности в реальном времени по соединениям.
*   `nethogs` — определение процессов, потребляющих трафик.
*   `arp-scan` / `netdiscover` — обнаружение устройств в локальной сети.
*   `dig` / `nslookup` — диагностика DNS, поиск misconfiguration и скрытых поддоменов.
*   `traceroute` / `mtr` — трассировка маршрута для диагностики сетевых проблем.

### 🔍 Аудит безопасности и поиск уязвимостей

*   `lsof -i -P -n` — список всех открытых сетевых соединений.

*   `auditctl` — управление аудитом системы (из пакета `auditd`).
*   `pscap` / `capsh` — проверка Linux-способностей (capabilities) процессов и бинарных файлов.
*   `lscpu` — отображает уязвимости процессора (например, Spectre, Meltdown).

## 🤖 DeepSeek

Вот ключевые команды для диагностики дисковой подсистемы, программных RAID-массивов и Ceph.

### 💾 Дисковая система общего назначения
*   **Общая информация**: `lsblk` — иерархия всех дисков и разделов; `sudo fdisk -l` — таблицы разделов всех дисков.
*   **Использование**: `df -h` — заполненность файловых систем; `sudo du -sh *` — размер папок.
*   **LVM**: `sudo pvdisplay`, `vgdisplay`, `lvdisplay` — детали физических томов, групп и логических томов.

### 🗄️ Программный RAID (mdadm)
*   **Общий статус**: `cat /proc/mdstat` — быстрый просмотр состояния всех RAID-массивов.
*   **Детальная информация**: `sudo mdadm --detail /dev/md0` — подробности о конкретном массиве (`/dev/md0`): уровень, состояние, список дисков.

### 🌐 Распределённое хранилище Ceph
*   **Общий статус**: `ceph status` и `ceph health detail` — состояние всего кластера, предупреждения.
*   **Диски (OSD)**: `ceph osd stat` / `ceph osd tree` — кол-во и состояние OSD (в работе/нет); `ceph df` — свободное место в пулах.
*   **Устройства**: `sudo ceph device ls` — список физических дисков, отслеживаемых Ceph; `sudo ceph device ls-by-host <host>` — диски на конкретном хосте.
*   **Группы (PG)**: `ceph pg stat` — статус групп объектов (все должны быть `active+clean`); `ceph pg dump_stuck` — поиск проблемных PG.
*   **Инвентаризация хоста**: `sudo ceph-volume inventory` — информация и пригодность всех дисков на узле для Ceph.
*   **Поиск проблем**: `sudo dmesg -T | grep -i -E "i/o error|sector|Prefailure"` — просмотр ошибок ввода-вывода в логах ядра.
*   **Привязка OSD к диску**: `sudo ceph device ls-by-host <host> | grep <диск>` — найти, какой OSD работает на диске (например, `sdk`).

Если нужна помощь по конкретному сценарию (например, замене диска), скажите.

## 🤖 DeepSeek

Вот четкое разделение: как проверить **сами диски** (физические ошибки) и как заподозрить неисправность **RAID-контроллера** (аппаратного).

---

### 🔬 Проверка физических дисков на ошибки (Bad Blocks / S.M.A.R.T.)

*   **S.M.A.R.T. (прогнозирование отказа)**:
    *   `sudo smartctl -a /dev/sda` — полный отчет атрибутов. Критические поля: **Reallocated_Sector_Count** (переназначенные сектора), **Current_Pending_Sector** (ожидающие), **Offline_Uncorrectable**.
    *   `sudo smartctl -t long /dev/sda` — запуск фонового расширенного теста (занимает часы). Статус смотрите через `smartctl -l selftest /dev/sda`.
*   **Поверхностная проверка (чтение всего диска)**:
    *   `sudo badblocks -sv /dev/sda` — побайтовая проверка на битые блоки (очень нагружает диск, лучше делать в однопользовательском режиме).
*   **Быстрый поиск ошибок в ядре**:
    *   `sudo dmesg -T | grep -i -E "i/o error|sector|scsi|sd[a-z]|read error|write error"` — мгновенный показ ошибок ввода-вывода за время работы системы.

---

### 🖥️ Диагностика аппаратного RAID-контроллера

Главный признак проблем с контроллером — **диски в BIOS видны, а ОС их не видит**, либо система зависает при обращении к массиву.

*   **LSI / Broadcom (MegaRAID)**:
    *   `sudo storcli /c0 show` — общая информация о контроллере (модель, прошивка).
    *   `sudo storcli /c0 /eall /sall show` — все физические диски.
    *   `sudo storcli /c0 /v0 show` — состояние логического тома.
    *   `sudo storcli /c0 /eall /sall show all | grep -i "error\|health"` — поиск ошибок и сбойных дисков.
*   **HP SmartArray**:
    *   `sudo ssacli ctrl all show` — все контроллеры.
    *   `sudo ssacli ctrl slot=0 pd all show status` — состояние дисков (поддерживаются только *массивы*).
*   **Проверка кэша и батареи (частый источник зависаний)**:
    *   `sudo storcli /c0 show bbustatus` — статус батареи (BBU). Если батарея мертва или отсутствует, контроллер часто отключает кэш записи и тормозит или «пропадает».
    *   `sudo ssacli ctrl slot=0 show` — у HP батарея и кэш показываются в общем выводе.
*   **Диагностика зависаний**:
    *   `sudo storcli /c0 show events` — лог событий контроллера (зависания, сбросы).
    *   В HP посмотрите журнал IML: `sudo ssacli ctrl slot=0 diag` (или через `hpasmcli`).

---

### ⚠️ Быстрый чек-лист: «Контроллер или диск?»

| Симптом | Вероятная причина |
| :--- | :--- |
| Ошибки в `dmesg` с конкретным `sdX` (например, `sdb`). | **Диск** (сбой секторов). |
| Диск горит зеленым в BIOS, но `smartctl` не работает, а `dmesg` полон таймаутов. | **Контроллер** (завис, перегрелся, проблема с прошивкой). |
| ОС не видит диски, но контроллер в BIOS видит массив как «Foreign» (Foreign). | **Контроллер сбросил конфигурацию** (нужно импортировать). |
| Падает сервер при записи больших файлов. | Проверьте **кэш и батарейку** (BBU) — отключите кэш записи, если она умерла. |

Если у вас **встроенный SATA-контроллер** (AHCI), а не дискретная RAID-карта, проблема почти всегда в диске или кабеле/питании.

> **Важно:** Запуск `badblocks` на дисках, входящих в аппаратный RAID, **категорически запрещен** — это разрушит массив. Для проверки таких дисков используйте только **S.M.A.R.T.** и утилиты самого контроллера (`storcli` / `ssacli`).

## 🤖 DeepSeek

Диагностика шлейфов (кабелей) SAS/SATA — это самая хитрая часть, потому что софт не видит кабель напрямую. О неисправности говорят **косвенные признаки**: сбои, сбросы ссылки (link resets) и растущие счетчики ошибок.

Вот пошаговая стратегия, как «поймать» плохой кабель:

---

### 1. Главные «красные флаги» в системных логах

Плохой кабель почти всегда дает **прерывистые ошибки**. Откройте логи ядра в реальном времени и смотрите на поведение диска:

```bash
sudo dmesg -T -w | grep -i -E "link|reset|scsi|sd[a-z]|abort|error|timeout|revalidate"
```

**Критические фразы для кабеля:**
- `link reset` / `phy reset` — сброс физического соединения (кабель плохо контачит).
- `SATA link down` / `SATA link up` — диск постоянно «переподключается».
- `hard reset` / `soft reset` — контроллер перезапускает канал.
- `INQUIRY failed` / `revalidation failed` — диск «пропадает» на секунду и возвращается.
- `I/O error` с разными `sdX` (если ошибка прыгает по дискам) — чаще всего виноват кабель или бэкплейн (корзина).

Если ошибки привязаны строго к одному диску (`sdg`) — скорее сам диск. Если ошибки хаотично на разных дисках в одной корзине — **проверяйте кабель или разъем**.

---

### 2. Счетчики ошибок SCSI / SAS (самый точный метод)

Современные HBA/RAID-контроллеры ведут статистику по каждому физическому каналу (phy).

- **Для LSI / Broadcom (storcli):**
  ```bash
  sudo storcli /c0 /eall /sall show all | grep -i -E "error|link|phy|speed|bad|realloc"
  ```
  Ищите параметры: `Link Speed`, `Link Status`, `Media Error Count`, `Other Error Count`. Если `Other Error Count` растет, а `Media Error` — нет, это почти 100% кабель или разъем.

- **Для HP SmartArray (ssacli):**
  ```bash
  sudo ssacli ctrl slot=0 pd all show detail | grep -i -E "error|status|failed|link"
  ```
  Обратите внимание на параметры с приставкой `ER` (Error Rate).

- **Прямой опрос SMART (атрибуты намекают на кабель):**
  ```bash
  sudo smartctl -a /dev/sda | grep -i -E "ultra|crc|error|udma"
  ```
  Критические атрибуты, указывающие на кабель:
  - **UltraDMA CRC Error** (ID 199 для SATA) — битые пакеты по кабелю. Если это число растет — **меняйте кабель немедленно**.
  - **SATA PHY Replay Count** / **SATA Link Retry** — диск переспрашивает команды из-за помех.

---

### 3. Проверка скорости линка (должна быть стабильной)

Плохой кабель заставляет контроллер понижать скорость (падение с 6 Гбит/с до 3 или 1.5 Гбит/с).

- **Проверьте текущую скорость:**
  ```bash
  sudo smartctl -l sataphy /dev/sda   # для SATA
  sudo lsscsi -t                      # показывает тип и скорость подключения
  ```
- **Сравните** с эталонной скоростью диска. Если диск на 6 Гбит/с, а висит на 3 Гбит/с — кабель не держит частоту.

---

### 4. Физическая проверка (Hardware)

Если цифры указывают на кабель, сделайте следующее:

1. **Замена мест** — поменяйте кабель от проблемного диска с заведомо рабочим. Если ошибка **переместилась** на другой диск — кабель виноват.
2. **Осмотр разъемов** — ищите окисление, погнутые контакты, трещины в защелке. Особенно страдают корзины (бэкплейны) — часто виноват не сам кабель, а переходник на плате корзины.
3. **Плотность посадки** — при вибрации серверов кабель может «отходить» от разъема. Попробуйте аккуратно поджать или перефиксировать.

---

### 5. Специфика: SAS против SATA

- **SAS** (кабель-шлейф толще) — ошибки чаще выдают `phy resets` и `hard reset`. Если у вас SAS-диски, обратите внимание на **двойные пути** (multipath). Иногда один из путей умер — смотрите `multipath -ll`.
- **SATA** — главный индикатор **UltraDMA CRC**. Если счетчик больше 10 и растет — кабель под замену без вариантов.

---

### ⚠️ Важное предостережение

Никогда не меняйте кабель «на горячую» на SATA-дисках без горячей замены (без бэкплейна) — это жжет контроллер. Выключайте сервер или отключайте питание корзины перед заменой шлейфа.

> **Итог:** Если видите, что ошибки `UltraDMA CRC` или `Link Resets` растут, а на диске нет битых секторов (Reallocated_Sector = 0) — **меняйте кабель**. Это дешевле замены диска и потери данных.

## 👤 Пользователь

Команды проверки оперативной память

## 🤖 DeepSeek

Диагностика оперативной памяти в Linux делится на **быструю проверку** (поиск очевидных сбоев) и **глубокое тестирование** (поиск битых ячеек). Вот полный арсенал:

---

### 🚀 Быстрая проверка (логи и статус)

Прежде чем запускать тяжелые тесты, проверьте, не жалуется ли на память сама система:

```bash
# 1. Ошибки памяти в логах ядра (ECC-память или крахи)
sudo dmesg -T | grep -i -E "hardware error|edac|mce|bank|corrected error|uncorrected error|machine check"

# 2. Сбор статистики по ошибкам ECC (если серверная память)
sudo ras-mc-ctl --summary        # Общая статистика коррекций
sudo ras-mc-ctl --errors         # Детальные ошибки по каналам

# 3. Использование swap (косвенный признак нехватки или сбоев)
cat /proc/meminfo | grep -E "MemTotal|MemFree|SwapTotal|SwapFree"
vmstat 2 10                      # si/so (swap in/out) — если > 0, памяти мало
```

Если в `dmesg` есть `Hardware Error` или `CE` (Corrected Error) — память деградирует.

---

### 🧪 Полное тестирование памяти (Memtest86+)

Это **золотой стандарт**. Тест грузится вне ОС и проверяет каждый бит.

```bash
# Установить загрузчик memtest
sudo apt install memtest86+        # Debian/Ubuntu
sudo dnf install memtest86+        # RHEL/Fedora

# После установки перезагрузитесь и выберите в GRUB пункт "Memtest86+"
# Рекомендуется прогнать минимум 1 полный проход (Pass) — это часы.
```

**Если нет доступа к консоли** — можно запустить из ОС, но это менее надежно:

```bash
# memtester (работает в пользовательском пространстве, но найдет грубые ошибки)
sudo apt install memtester
sudo memtester 1G 3               # Тест 1 ГБ памяти 3 прохода (займет ~10 мин)
```

---

### 📊 Мониторинг ошибок в реальном времени

```bash
# 1. EDAC (Error Detection And Correction) — смотрит на контроллер памяти
sudo modprobe edac_core
sudo ls /sys/devices/system/edac/mc/*/          # Посмотреть доступные каналы
cat /sys/devices/system/edac/mc/mc0/ce_count    # Количество исправленных ошибок
cat /sys/devices/system/edac/mc/mc0/ue_count    # Количество НЕисправленных (критично!)

# 2. Machine Check Exceptions (MCE) — ошибки CPU/памяти
sudo mcelog --client --daemon      # Запустить сервис сбора
mcelog --client --status           # Посмотреть накопленные ошибки
```

---

### 🔍 Поиск скрытых проблем (косвенные тесты)

Если ошибки плавающие (зависания, случайные крахи), попробуйте:

```bash
# 1. Нагрузить память и посмотреть на систему
stress --vm 4 --vm-bytes 1G --timeout 60s &     # Нагружает ОЗУ на 60 сек
watch -n 1 'cat /proc/meminfo | grep -E "MemFree|Cached|SwapFree"'

# 2. Проверка /proc/iomem (конфликты адресов)
cat /proc/iomem | grep -i memory

# 3. Сброс SPD (данных модуля) — если неправильно определилась частота
sudo dmidecode -t memory | grep -E "Speed|Type|Rank|Error Correction"
```

---

### ⚡ Опасные симптомы (когда менять память срочно)

| Симптом | Действие |
| :--- | :--- |
| `Uncorrected Error` в `dmesg` | **Немедленная замена** — данные уже повреждены |
| `Corrected Error` растет каждый час | Менять в течение недели — деградация ускоряется |
| Memtest показывает **хоть одну красную строку** | Менять модуль. Попытки переставить в другой слот — бесполезны |
| Сервер перезагружается без логов | Запустите Memtest — скорее всего битая ячейка в области ядра |

---

### 💡 Лайфхаки для серверов

- **Горячая замена** (если поддерживается): `echo 1 > /sys/bus/pci/devices/0000:00:00.0/remove` — но проще выключить сервер.
- **Проверка парности** (для ECC): `sudo edac-ctl --mainboard` — показывает, корректно ли распознаны планки.
- **Если Memtest недоступен**: загрузитесь с Live USB любого Linux-дистрибутива и запустите `memtester 2G 5` — найдет грубые ошибки за 20 минут.

> **Золотое правило:** Ошибки памяти лечатся **ТОЛЬКО заменой модуля**. Никакие софтовые фиксы (отключение кэша, понижение частоты) не дают гарантии — только откладывают проблему.

## 👤 Пользователь

Команды проверка и мониторинг питания

---

## 🤖 DeepSeek

Диагностика питания в Linux — это **косвенная наука**, так как ОС не видит вольты напрямую (без спецдатчиков). Но систему можно научить фиксировать **признаки проблем**: просадки, перегрузку линий и сбои оборудования.

Вот полный набор команд и методик:

---

### ⚡ Мониторинг напряжения (IPMI / BMC)

Если сервер с **IPMI** (HP iLO, Dell iDRAC, Supermicro):

```bash
# Установите утилиту ipmitool
sudo apt install ipmitool   # Debian/Ubuntu
sudo dnf install ipmitool   # RHEL/Fedora

# 1. Полный список сенсоров напряжения
sudo ipmitool sdr list | grep -i voltage
sudo ipmitool sensor list | grep -E "Voltage|Vcore|Vbat|P12V|P5V|P3V"

# 2. Мониторинг в реальном времени
watch -n 5 'sudo ipmitool sensor list | grep -E "Voltage|PS|Power"'

# 3. История событий питания (падения, отключения)
sudo ipmitool sel list | grep -i -E "power|voltage|under|over"
```

**Для HP** (специфично):
```bash
sudo hpasmcli -s "show powersupply"          # Статус всех PSU
sudo hpasmcli -s "show powersupply status"   # Работают ли оба блока
sudo hpasmcli -s "show voltages"             # Текущие вольтажи
```

**Для Dell** (через OMSA):
```bash
sudo omreport chassis pwrsupplies           # Статус блоков питания
sudo omreport chassis volts                # Напряжение на шинах
```

---

### 🔌 Проверка блоков питания (PSU) и резервирования

```bash
# 1. Косвенная проверка через лог событий (если сервер перезагружался)
sudo dmesg -T | grep -i -E "power|power supply|psu|over voltage|under voltage|brownout"

# 2. Статус питания через ACPI (ноутбуки / UPS)
cat /proc/acpi/battery/BAT0/info           # Информация о батарее
cat /proc/acpi/battery/BAT0/state          # Текущий заряд / потребление

# 3. Для систем с UPS (NUT - Network UPS Tools)
sudo apt install nut-client nut-snmp
upsc ups_name@localhost                     # Статус ИБП
```

---

### 🖥️ Поиск «тихих» проблем питания в логах

Плохой блок питания часто ведет к странным сбоям:

```bash
# 1. Сброс PCI-устройств / пропадание дисков (признак просадки)
sudo dmesg -T | grep -i -E "link down|link up|reset|abort|timeout|power fault"

# 2. Если диск отключается и подключается — проверяйте линии питания
sudo journalctl -f -k | grep -i -E "sd[a-z]|scsi|ata"

# 3. Ошибки ECC памяти могут быть вызваны плохим питанием (а не памятью!)
sudo ras-mc-ctl --errors | grep -i voltage
```

---

### 🛠️ Тестирование под нагрузкой (провокация просадок)

```bash
# 1. Нагрузить все диски (чтобы проверить линии 12V/5V)
sudo fio --name=stress --rw=randrw --size=10G --numjobs=4 --time_based --runtime=120

# 2. Одновременно нагрузить CPU (просадка по 12V)
sudo stress --cpu 8 --io 4 --vm 2 --vm-bytes 2G --timeout 120s &

# 3. В параллельном окне мониторить сенсоры
watch -n 2 'sudo ipmitool sensor list | grep -E "P12V|P5V|P3V"'
```

**Если напряжение проседает более чем на 5% от номинала** — блок питания либо перегружен, либо умирает.

---

### 📊 Профилактический скрипт (каждые 5 минут)

Создайте файл `/usr/local/bin/check_power.sh`:

```bash
#!/bin/bash
# Мониторинг питания
echo "=== $(date) ===" >> /var/log/power_monitor.log

if command -v ipmitool &> /dev/null; then
    ipmitool sdr list | grep -E "Voltage|Power" >> /var/log/power_monitor.log
fi

# Если напряжение упало ниже 11.8V (для 12V линии) — шлем alert
VOLT=$(ipmitool sensor list | grep "P12V" | awk '{print $4}')
if (( $(echo "$VOLT < 11.8" | bc -l) )); then
    echo "WARNING: Low voltage! $VOLT V" >> /var/log/power_monitor.log
fi
```

Сделайте исполняемым и добавьте в `cron`:
```bash
chmod +x /usr/local/bin/check_power.sh
crontab -e
*/5 * * * * /usr/local/bin/check_power.sh
```

---

### ⚠️ Критические признаки неисправного питания

| Симптом | Диагноз |
| :--- | :--- |
| Сервер **выключается** при нагрузке | Блок питания не тянет пиковые ватты |
| **Разные диски** отваливаются в случайном порядке | Просадка по линии 12V |
| Ошибки памяти **без битых ячеек** в Memtest | Нестабильное питание чипов памяти |
| В логах `power fault` или `under voltage` | Срочно менять PSU (желательно оба) |
| Вентиляторы крутятся на максимуме | Косвенный признак проблем с питанием (сбой датчиков) |

---

### 💡 Железный лайфхак

Самый надежный способ — **мультиметр** на разъеме Molex/SATA в момент нагрузки. Но если сервер удаленный — смотрите на `ipmitool` и **журналы SEL** (System Event Log). Если там есть записи о `Power Supply Failure` или `Voltage excursion` — меняйте блок, не дожидаясь полного отказа.

> **Важно:** Все серверные блоки с горячей заменой имеют два режима: `Redundant` (оба работают) и `Standby` (один в резерве). Если один PSU умер, второй берет нагрузку, но лог покажет `Power Supply Lost`. Игнорировать это нельзя — при скачке напряжения упадет весь сервер.

## 👤 Пользователь

Проверка исправности дисковой корзины

---

## 🤖 DeepSeek

Диагностика дисковой корзины (Backplane / Drive Cage / Enclosure) — одна из самых сложных задач, потому что корзина — это «пассивный» (или полуактивный) компонент. Ошибки часто маскируются под проблемы с дисками или кабелями.

Вот полный арсенал проверок:

---

### 1. Первичные «флаги» в логах

Откройте логи ядра в реальном времени и ищите паттерны:

```bash
sudo dmesg -T -w | grep -i -E "ses|enclosure|sas|expander|phy|link reset|smp|broadcast"
```

**Критические паттерны, указывающие на корзину (а не диск):**
- `SES: enclosure` или `Enclosure Service` — ошибка связи с микроконтроллером корзины.
- `Broadcast (SES)` — сброс всей корзины (признак проблем с питанием или управлением).
- `Link reset` на **нескольких** дисках одновременно — корзина «перезагружается».
- `SAS expander` ошибки — корзина с активным расширителем не отвечает.
- `phy` ошибки на разных портах — битый бэкплейн.

---

### 2. Проверка через `lsblk` и `lsscsi` (иерархия)

```bash
# 1. Посмотреть топологию — где диск подключен (через какой интерфейс/контроллер)
sudo lsscsi -g

# 2. Если диски висят на одном Enclosure, их идентификатор корзины совпадает
lsblk -S                    # Показывает имя HBA и модель
sudo smartctl -i /dev/sda | grep -i "device model\|serial number"
```

Если **все диски одной корзины** имеют одинаковый `Enclosure ID` в `smartctl` — проверяйте питание корзины.

---

### 3. Счетчики ошибок через SES (SCSI Enclosure Services)

Самый точный метод — опросить встроенный контроллер корзины (если он есть):

```bash
# 1. Установить утилиту sg3_utils
sudo apt install sg3-utils           # Debian/Ubuntu
sudo dnf install sg3_utils           # RHEL/Fedora

# 2. Найти устройство корзины (обычно /dev/sg*)
sudo ls -l /dev/sg*                  # Ищем non-disk устройства
sudo sg_ses -A /dev/sgX              # X — номер устройства корзины

# 3. Проверить статус слотов, вентиляторов, датчиков температуры
sudo sg_ses --status /dev/sgX        # Общее состояние
sudo sg_ses --get=temp /dev/sgX      # Температура в корзине
sudo sg_ses --get=power /dev/sgX     # Статус питания слотов
```

**Если команда выдает ошибку `Invalid opcode`** — корзина пассивная (без SES), переходите к косвенным методам.

---

### 4. Косвенные тесты (если SES недоступен)

#### А. Проверка перегревом (самая частая причина сбоев)

```bash
# 1. Температура всех дисков через SMART
for i in /dev/sd{a..z}; do echo -n "$i: "; sudo smartctl -A $i | grep -i "Temperature" | awk '{print $10}'; done

# 2. Если температура дисков в корзине отличается на 10+ градусов — плохая вентиляция или сгоревший вентилятор
```

#### Б. Проверка питания корзины

```bash
# 1. Посмотреть, есть ли ошибки питания у всех дисков одновременно
sudo dmesg -T | grep -i -E "power fault|over current|voltage"

# 2. Если при нагрузке отваливаются диски из разных слотов — проблема в питании корзины
sudo fio --name=stress --rw=randrw --size=10G --numjobs=4 --time_based --runtime=60
# В параллельном терминале: dmesg -T -w | grep -i reset
```

#### В. Проверка целостности бэкплейна (пропавшие слоты)

```bash
# 1. Просканировать SCSI-шину (заставляет контроллер перечитать корзину)
echo 1 > /sys/class/scsi_host/host0/scan   # host0 — ваш HBA
lsblk -S                                   # Проверить, появились ли новые диски

# 2. Если после скана часть дисков не появилась — слот умер (замена корзины)
```

---

### 5. Тест перестановкой (железный метод)

Это самый надежный способ диагностики:

1. **Поменяйте местами диски** внутри корзины (слот A ↔ слот B).
2. Посмотрите:
   - Если ошибка **переместилась** со слотом — **слот/питание корзины** (меняйте корзину).
   - Если ошибка **осталась** на диске — проблема в **самом диске**.

**Важно:** Делайте это только на выключенном сервере (если нет горячей замены)!

---

### 6. Специфичные проверки для SAS Expander

Если в корзине стоит SAS-расширитель (активный бэкплейн), проверьте его:

```bash
# 1. Информация о расширителе
sudo smp_discover /dev/sgX      # X — устройство расширителя
sudo smp_phy_control -i /dev/sgX

# 2. Статистика по phy (каналам)
sudo smp_phy_info /dev/sgX | grep -i -E "attached|error|disabled"

# 3. Если phy-порты отключены сами — расширитель перегрет или умирает
```

---

### 7. Логи контроллера (HBA/RAID)

Если диски в корзине висят на SAS-контроллере:

```bash
# LSI / Broadcom
sudo storcli /c0 /eall show          # Показать все корзины (enclosures)
sudo storcli /c0 /eall show fault     # Есть ли ошибки в корзине
sudo storcli /c0 show events         # Журнал событий

# HP SmartArray
sudo ssacli ctrl slot=0 enclosure all show   # Статус корзин
sudo ssacli ctrl slot=0 show config detail   # Общий статус
```

---

### ⚠️ Критические признаки неисправной корзины

| Симптом | Вердикт |
| :--- | :--- |
| Диски в **разных слотах** дают одинаковые ошибки (`reset`, `timeout`) | **Корзина** (проблема с бэкплейном) |
| При нагрузке отваливается **группа дисков** (не один) | **Питание корзины** — просадка 12V |
| Вентиляторы корзины не крутятся, температура дисков > 50°C | Замена вентиляторов или всей корзины |
| `sg_ses` не видит корзину, хотя диски работают | Умер микроконтроллер SES (нужна замена) |
| При вставке диска слот не видит его, а другой слот видит | **Конкретный слот умер** — корзина в ремонт |

---

### 💡 Последний рубеж: обновление прошивки

Иногда проблемы с корзиной лечатся прошивкой (особенно у Dell/HP):

```bash
# Проверить версию прошивки корзины
sudo dmidecode -t system | grep -i firmware

# Обновлять ТОЛЬКО через официальный образ от производителя
```

> **Итог:** Если после замены кабелей и проверки дисков ошибки остаются, и они **плавают по слотам** — меняйте дисковой корзину/бэкплейн. Дешевле потерять 1 корзину, чем 12 дисков и данные.
